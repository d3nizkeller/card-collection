# Мобильная стабилизация «Коллекционера карт»

Цель: игра перестала вылетать и закрывать браузер/WebView на телефонах и в
Telegram Mini App, при этом **визуально и функционально ничего не потеряно**.

Всё измерено headless-Chromium в эмуляции iPhone 12 (DPR 3, как в Telegram
Mini App): оригинал против новой сборки, по 9 экранам с обходом разделов.
Скриншоты «до/после» лежат в `tools/shots/`.

---

## 1. Что роняло игру (диагноз, по убыванию вреда)

### 1.1. Распакованные битмапы: до 522 МБ потенциально, 63 МБ на стартовом экране
Каталог карт приходит **из облака комнаты** (textdb.dev) и ссылается на файлы
`media/card_*.png` размером **1080×1920 и 1152×2048**. В HTML этих имён нет,
поэтому казалось, что файлы «не используются» — на самом деле они рабочие.

Распакованная битмапа = ширина × высота × 4 байта:

| арт | в памяти | показывается в размере |
|---|---|---|
| 1152×2048 | **9.00 МБ** | 76–176 css px |
| 1080×1920 | **7.91 МБ** | 76–176 css px |
| 768×1376  | 4.23 МБ | ~176 css px |

Стартовый экран (витрина + 3D-карусель паков) держал **63.2 МБ битмапов на
12 картинках**. Весь каталог — **522 МБ**. iOS/Android убивают WebView задолго
до этого: отсюда «игра вылетает», «браузер сам закрылся».

Картинки грузились в полный размер даже там, где рисуются на холст 224×512
(`loadImgSafe` → текстура пака для three.js) и в списках по 28–48 px.

### 1.2. Tailwind Play CDN работал прямо в браузере
В `index.html` был зашит JIT-компилятор Tailwind (398 КБ: сам компилятор +
PostCSS + autoprefixer). Он вешал `MutationObserver` на весь документ
(`childList, subtree`) и при **любой** мутации DOM прогонял весь CSS через
PostCSS: замер на десктопе — 554 мс холодного прогона, на телефоне ×3–5.
В игре 171 место с `innerHTML =` — то есть пересборка CSS случалась постоянно,
блокируя главный поток посреди анимаций и WebGL. Это главный источник
«тормозит и подвисает».

Замер длинных задач (>50 мс) главного потока: **оригинал — 75 задач, 6.1 с
суммарно; новая сборка — 23 задачи, 1.8 с (−71 %)**.

### 1.3. 3.2 МБ одним файлом, без кеширования
`index.html` = 3.25 МБ: Tailwind (398 КБ) + three.js r128 (589 КБ) + Font
Awesome (686 КБ, причём **один и тот же woff2 по 150 КБ встроен base64 три
раза**) + qrcode (147 КБ) + код игры (996 КБ) + разметка. Плюс три мета-тега
`Cache-Control: no-cache` — часть WebView честно их выполняла и качала всё
заново при каждом открытии.

### 1.4. Font Awesome целиком + 404 на шрифты
686 КБ CSS на ~2000 иконок при **189 используемых**. Плюс 7 ссылок
`url(../webfonts/…)`, которых в репозитории нет — 7 гарантированных 404.

### 1.5. Google Fonts блокировал отрисовку
`<link rel="stylesheet" href="https://fonts.googleapis.com/…">` —
render-blocking. В России и в ряде WebView этот хост недоступен: страница
висела до сетевого таймаута («белый экран»). При этом Inter в CSS не
используется нигде, кроме надписей на canvas.

### 1.6. Мелочи, которые складывались
- Сторож памяти срабатывал при heap > 350 МБ, но на слабых Android
  `jsHeapSizeLimit` ≈ 256 МБ — порог не достигался **никогда**, сторож молчал.
- На iOS Safari `performance.memory` нет вообще — там сторож не работал вовсе.
- `<img>` без `loading="lazy" decoding="async"` в 19+42 местах → браузер
  декодировал все картинки списка сразу.
- Watchdog картинок сканировал `document.images` каждые 6 с даже в фоне.
- Telegram: не вызывались `disableVerticalSwipes()` /
  `enableClosingConfirmation()` — свайп сверху вниз случайно закрывал
  мини-апп во время анимаций («игра сама закрылась»).
- Предзагрузка `preloadAllGameImages()` ставила в очередь **полные арты**
  всего каталога: ~157 МБ фонового трафика на старте облачной комнаты.
- Две иконки использовались из Font Awesome **Pro** (`fa-sack-coins`,
  `fa-sparkles`) — в Free их нет, они рисовались пустым квадратом.

### 1.7. Страница растягивалась пинчем и двойным тапом
Жалоба игроков: случайный щипок или двойной тап «растягивает» сайт, раскладка
уезжает. Воспроизведено: оригинал после пинча ×2.2 даёт
`visualViewport.scale = 2.2` и остаётся в нём. Причина — в viewport не было
ограничений масштаба, а `touch-action` нигде не задавался.

## 2. Что сделано

### 2.1. Три уровня артов (главное исправление)
```
media/t/   256 px WebP  — списки, строки, компактные сетки, шапки   (~0.47 МБ в памяти)
media/t2/  512 px WebP  — обычные сетки альбома, вскрытие пака,
                          витрина, 3D-карусель, текстуры three.js    (~1.8 МБ в памяти)
мастер     без изменений — просмотр карты и вид «галерея» (1:1, как было)
```
- Миниатюры построены для **всех 156 картинок** `media/` (включая облачные
  `card_*`), а не только для упомянутых в HTML.
- Полноразмерные арты **не пережаты и не удалены**: там, где карта крупная,
  картинка осталась ровно той же. Ничего визуально не изменилось.
- `nxThumbFor()` умеет строить путь миниатюры и для абсолютных облачных ссылок
  (`https://…/media/card_x.png` → `https://…/media/t2/card_x.webp`).
- Страховка: если миниатюры нет (файл добавили после сборки) — `imgErrorChain`
  по атрибуту `data-nx-full` мгновенно подставляет полный арт. Заглушек нет.
- `loadImgSafe()` (текстуры three.js) теперь берёт 512 px вместо 1152×2048:
  холст текстуры всё равно 512×768, качество идентично, а памяти в 5 раз меньше.
- `preloadAllGameImages()` греет миниатюры: **~3 МБ фонового трафика вместо ~157 МБ**.

### 2.2. Tailwind прекомпилирован
`assets/tailwind.css` (122 КБ, 1279 правил) собран один раз из **всего**
исходника — так в CSS попали и классы разметки, и пулы строк из JS
(`${getRarityClass()}`, `cls[o.r]`, `meta.color` …), поэтому ни один
динамический класс не потерян. JIT-компилятора в странице больше нет.
Пересобрать: `python3 tools/build.py --tw` (нужен `npm i` в корне).

### 2.3. Разбиение на кешируемые файлы
```
index.html               264 КБ   (было 3.25 МБ)
assets/app.js          1 032 КБ   код игры
assets/three.min.js      589 КБ   defer — не блокирует парсинг, нужен только 3D
assets/qrcode.min.js     147 КБ
assets/qr-transfer.js     96 КБ
assets/stories.js         35 КБ
assets/app.css            94 КБ   + правила .nx-cv / safe-area
assets/tailwind.css      120 КБ
assets/fa.css             22 КБ   подмножество FA
assets/fa-solid-900.woff2 18 КБ   один файл вместо трёх base64-копий
```
Первый визит ≈ 2.36 МБ несжатых (~0.66 МБ по gzip), повторный — всё из кэша.
Кеш-бустинг: `?v=nxmob5` + service worker.

### 2.4. Font Awesome — подмножество
187 иконок из ~2000, один woff2 18.5 КБ. 686 КБ → 41 КБ суммарно.
Убраны 7 мёртвых `url(../webfonts/…)` (404). Две Pro-иконки заменены на
бесплатные аналоги: `fa-sack-coins → fa-sack-dollar`, `fa-sparkles → fa-wand-magic-sparkles`.

### 2.5. Отложенная отрисовка длинных списков
`.nx-cv { content-visibility: auto; contain-intrinsic-size: auto 300px }` на
карточках альбома и лотах биржи: браузер не считает layout и не рисует то, что
за экраном. В альбоме/на бирже бывает 100–300 карточек — это был главный
источник подвисаний при прокрутке. Браузеры без поддержки правило игнорируют.

### 2.6. Мобильные/Telegram-правки
- Убраны `no-cache` мета-теги; кешированием занимается `sw.js` (v2:
  `media/` и `assets/` — вечный cache-first, HTML — network-first).
- `viewport-fit=cover` + safe-area-отступы под вырез и нижнюю полосу iPhone.
- Google Fonts подключён неблокирующе (`media="print" onload=…`) + `<noscript>`.
- Telegram: `expand()`, `disableVerticalSwipes()`, `enableClosingConfirmation()`,
  пересчёт `resize` при `viewportChanged`; сохранение прогресса на
  `pagehide / freeze / visibilitychange` (WebView Telegram замораживают, а не
  закрывают — раньше прогресс терялся).
- Сторож памяти: порог стал относительным (`min(350, 55 % jsHeapSizeLimit)`),
  плюс новый сторож битмапов, работающий без `performance.memory` (iOS):
  считает распакованные битмапы видимых `<img>` и при >160 МБ выгружает `src`
  у крупных картинок за экраном.
- `loading="lazy" decoding="async"` добавлены всем `<img>` (19 в JS + 42 в разметке…
  итог: всем, у которых их не было).
- Watchdog картинок и фоновые сканы не работают при `document.hidden`.
- `nxPixelRatio()` учитывает `navigator.deviceMemory/hardwareConcurrency`:
  на устройствах с ≤3 ГБ DPR рендереров режется до 1.0 (канвас 1080×1920 при
  DPR 3 = 74 МБ видеопамяти на один рендерер).

### 2.7. Запрет случайного масштабирования (пинч / двойной тап)
Три уровня защиты, потому что iOS 10+ и WKWebView игнорируют `user-scalable=no`:
1. `viewport`: `maximum-scale=1.0, user-scalable=no` — закрывает Android
   Chrome/WebView и старые iOS;
2. CSS `html, body { touch-action: pan-x pan-y }` — запрещает pinch-zoom и
   double-tap zoom, оставляя прокрутку по обеим осям и обычные тапы; полям ввода
   оставлен `touch-action: manipulation`;
3. JS: отмена `gesturestart/gesturechange/gestureend` (системные жесты Safari),
   `dblclick`, `ctrl+wheel`, `ctrl+ +/- /0`.

**Исключение:** у нарезчика сторис (`#s9-view`) собственный пинч (масштаб кадра)
и перетаскивание рамки — там `touch-action: none`, иначе браузер забирал бы
жест двух пальцев себе и редактор ломался (`pointercancel`).

Проверено CDP-пинчем в headless Chromium: оригинал — `scale = 2.2` после жеста,
новая сборка — `scale = 1` после пинча ×2.2, второго пинча и двойного тапа;
прокрутка (scrollY 0 → 600) и тапы по навигации работают как раньше.

## 4. Как пересобрать после правок игры

Ваш генератор по-прежнему делает монолит `index.html`. Новый порядок работы:

```bash
# 1. положите свежий монолит от генератора сюда:
cp путь/к/монолиту.html tools/source-index.html

# 2. пересоберите (миниатюры не пересоздаются, если арты не менялись):
python3 tools/build.py            # всё
python3 tools/build.py --no-media # быстрее, если media/ не трогали
python3 tools/build.py --tw       # + пересобрать Tailwind (нужен npm i)
python3 tools/build.py --force-media  # пересоздать миниатюры принудительно
```

Скрипт идемпотентен и падает с внятной ошибкой, если монолит изменился так,
что патчи не узнаются (лучше упасть, чем молча собрать кашу).

Если вы добавили в игру **новый Tailwind-класс** — пересборка `--tw` не нужна:
`assets/tailwind.css` пересобирается из `tools/source-index.html` при каждой
сборке, а сканируется весь файл, включая строки в JS.

### Проверка перед деплоем
```bash
node tools/probe.js test http://127.0.0.1:8002/index.html 8002 out.json /tmp/shots
```
(нужен локальный `python3 -m http.server` в корне проекта; скрипт печатает
битмапы/heap по экранам и длинные задачи).

## 5. Что важно знать про deploy

1. На GitHub Pages нужно залить **новые папки** `assets/`, `media/t/`,
   `media/t2/` и новый `sw.js`, `index.html`. Без `media/t*` ничего не сломается
   (сработает фолбэк на полные арты), но выигрыш по памяти пропадёт.
2. `sw.js` v2 сам вычистит старые кэши при активации. Игрокам, у которых стоял
   v1, новая версия приедет при следующем открытии.
3. Файлы `media/card_m*` (157 МБ) **не удалялись** — они рабочие (облачный
   каталог). Теперь они почти не грузятся в память: вместо мастеров
   подставляются миниатюры.
4. Если когда-нибудь захотите убрать вес репозитория: можно вынести
   `media/t2/` (5.2 МБ) — тогда средние сетки откатятся на миниатюры 256 px.
   Менять код для этого не нужно.

## 6. Почему сайт крашился прямо во время игры (10.10.2026, правки b355–b360)

Жалоба: «во время игры сайт крашится». Причина оказалась не в одной игре, а в
двух независимых утечках, которые срабатывали **во время** игрового сеанса.

### 6.1. Автоотправка картинок в GitHub (главная причина)

В сайт встроен механизм `b343-media`: картинки из кэша устройства сами уходят
коммитом в `media/` репозитория. Он запускается **без участия игрока**:

* `setInterval(..., 5 * 60 * 1000)` — каждые 5 минут;
* `visibilitychange` — **каждый раз, когда игрок возвращается на вкладку**;
* `nxNoteCachedMedia()` — на каждую новую картинку в кэше (во время игры их
  появляются десятки).

Что он делал до правки:

1. `nxCollectPendingMedia()` поднимал **все** неотправленные арты в память
   вкладки одновременно (не «по одному», а сразу массивом блобов);
2. каждый блок кодировался в base64 и заворачивался в `JSON.stringify` — по
   замеру это ~70 мс на мегабайт, то есть ~11 с непрерывной работы главного
   потока на всю коллекцию;
3. `NX_MEDIA_PUSHING` ставился **после** сбора, поэтому несколько триггеров
   подряд запускали 2–3 сбора параллельно;
4. `NX_MEDIA_LAST` обновлялся только при успехе — при ошибке троттлинг «не
   чаще раза в 10 минут» не срабатывал, и всё это повторялось каждые 5 минут.

Замер (`tools/repro-crash.js`, headless Chromium, каталог сайта):

| показатель | до правки |
|---|---|
| артов в каталоге | 82 |
| поднимается в память за один сбор | **156.2 МБ** (все 82 сразу) |
| base64 + JSON по всем файлам | **11.4 с** главного потока, 56 длинных задач |
| тело одного запроса к GitHub | до **1.18 МБ** на арт 0.36 МБ (×3.3) |
| реакция Node-перехватчика на такой запрос | **process out of memory** |

На телефоне, где вкладка и так держит 3D-сцены и кэш картинок, это означало
«страница замерла на 10–30 с, потом браузер её убил» — ровно во время игры.

Кнопка «Вшить всё» (`nxPushEmbedded`) была ещё тяжелее: она собирала
`index.html` со **всеми** артами внутри как data-URL. Замер: только 8 артов —
**9.7 МБ** строки; на 82 арта вышло бы ~190 МБ строки и один запрос на ~250 МБ.

### 6.2. WebGL-контексты и rAF-циклы, которые никто не освобождал

`nx3dReleaseHidden()` отдавал браузеру контексты только трёх игр — Слотов,
Сетки и Колеса. **Линии** и **Арена** не освобождались никогда:

* `lines3dTick()` крутился до конца сессии, даже когда игрок ушёл в Магазин
  (замер: 1 живой контекст и 8 кадров/с вхолостую);
* `battle3d` жил, пока игрок крутил слоты, и освобождался только кнопкой «Выйти
  из боя»;
* при уходе на другую **вкладку** (`switchTab`) не освобождалось ничего;
* в фоновой вкладке все циклы продолжали считать кадры.

Отдельная мелочь, которая ломала диагностику: `const NX_TRAIL` был объявлен в
конце файла, а `nxTrail()` вызывался с самого начала — каждый вызов падал в
`ReferenceError` (TDZ), ошибка проглатывалась `try/catch`, и «чёрный ящик»
последних событий перед крашем всегда был пуст.

### 6.3. Что сделано

| правка | что делает |
|---|---|
| **b355** | `NX_TRAIL` объявлен до первого использования — диагностика снова пишет след событий; `IMG_OBJ_MAX` 40 → 18 (10 на устройствах с малой памятью): было до 320 МБ живых blob:URL |
| **b356** | `nx3dReleaseHidden()` освобождает также **Линии** и **Арену**; `switchTab()` отдаёт все 3D-контексты при уходе с вкладки «Игры» и поднимает 3D обратно при возврате; `linesEnsure()` заново зовёт `linesTry3D()` (раньше поле навсегда оставалось плоским) |
| **b357** | Все 3D-циклы (слоты, сетка, колесо, линии, арена, дурак, вскрытие пака) видят флаг `nx3dFrozen` и останавливаются, когда вкладка в фоне; при возврате цикл запускается тем же замыканием — без дублей |

### 6.5. Чем это проверялось

* `tools/repro-crash.js` — headless Chromium в мобильной эмуляции: считает
  созданные/живые WebGL-рендеры (хук `THREE.WebGLRenderer`), активные rAF-циклы

  автоотправку в GitHub через мок API. Режимы: `loop`, `hidden`, `push`, `b64`,

* `tools/apply_fix.py` — правки b355–b360 в виде списка «old → new». Применяется

  теряются при следующей сборке. Режимы: `check`, `assets`, `monolith`.
* `tools/sync_build_blocks.py` — пересчитывает абсолютные границы блоков в

```bash

python3 tools/sync_build_blocks.py      # границы блоков в build.py
python3 tools/build.py --no-media       # index.html + assets/*
```

сам вычищает старые, поэтому игроки получат новый код при следующем открытии.

### 6.6. b361: холостые коммиты авто-«вшивания»

Разбираясь с пушем, обнаружили в `main` коммит `7a2e45d «авто: вшитые арты из
игры (b330)»`, который **не менял в репозитории ничего** (diff дерева пустой).

Причина: авто-«вшивание» (`nxScheduleAutoPush`, проверка каждые 5 минут) берёт
`index.html` с живого сайта через `nxSrcGet()` и ищет в нём маркер
`const NX_EMBED_MEDIA = {`. Но после мобильной сборки (`b342`) этот маркер живёт
в `assets/app.js`, а не в `index.html` — то есть на разделённой сборке
«вшивание» физически не может ничего вшить. Файл тем не менее собирался в памяти
(вместе со всеми data-URL из кэша) и коммитился как есть.

Что сделано:

* собранное сравнивается с тем, что уже лежит в ветке, по **git-sha содержимого**
  (`nxGitShaOf` — SHA-1 от `blob <длина>\0<байты>` через `crypto.subtle`), и при
  совпадении коммита нет вовсе; проверка идёт **до** тоста «пушу коммит»;
  тест `tools/test-b361.js`: sha совпал, запросов на создание блоба/коммита/refs — 0;
* заодно убрано троение строки `nx3dPauseAll()` в стороже памяти (дефект
  предыдущего коммита: правка несколько раз применялась к уже правленому файлу).

Это же значит, что «Вшить файл в сайт» на разделённой сборке больше не может
случайно перезаписать `index.html` старой копией с живого сайта (такой коммит
откатил бы `?v=nxmob7` обратно на `nxmob6`, и service worker начал бы отдавать
старые `assets/` из кэша).

### 6.9. Что замер опроверг (важно для будущих правок)

Гипотеза «base64 склейкой `bin += String.fromCharCode(...)` квадратичен» **не
подтвердилась**: в V8 такая конкатенация идёт через rope-строки, то есть почти
линейно. Прямой замер `qrxB64` против переписанного варианта (массив кусков +
один `join`), байты идентичны:

| объём | `+=` (как было) | массив + `join` |
|---|---|---|
| 256 КБ | 5 мс | 62 мс |
| 2 МБ | 124 мс | 206 мс |

Поэтому правка `b362` (перевести `qrxB64` на `join`) **отменена** — она сделала
бы медленнее. `nxBytesToB64` в коде остаётся (он не быстрее и не медленнее, но
читается проще), а настоящая стоимость отправки — это **объём блобов, которые
держат в памяти одновременно**, и число запросов; именно их b359 и режет.

## 7. b363: «один IP = один пользователь» и определение устройств (панель «Пользователи»)

Раньше каждая запись реестра (`textdb.dev/api/data/nexus-tcg-jackpot-v2`,
слияние max-by-timestamp) — это один **браузер**: один человек с телефоном,
планшетом и рабочим ПК выглядел как три разных «игрока» (см. скриншот
запроса: три строки «Денис Keller»).

Что сделано:

1. **Клиент публикует о себе три новых поля** (`siteStatsSelfUpdate`, попадают в
   `siteStatsDoc` и разносятся merge-ом всем):
   * `did` — устойчивый ID браузера (`nx_device_id` в localStorage), переживает
     перезаходы и позволяет узнать устройство даже без IP;
   * `dev` — портрет устройства из userAgent: ОС с версией, браузер (включая
     Telegram/Яндекс), форм-фактор (телефон/планшет/ПК), экран с DPR, ядра и
     память. Пример: `Android 14 · Chrome · телефон · 393×851@2.75x · 8 яд., 4 ГБ`;
   * `ip` — публичный IP: один запрос в 6 часов к `api.ipify.org`
     (фолбэки `api64.ipify.org`, `ifconfig.co`), кэш в localStorage, при
     недоступности сервисов — пусто и повтор не чаще раза в 10 минут. Первый
     ответ подхватывается следующим heartbeat (30 с), запросы фоновые и ничего
     не блокируют.
2. **Панель группирует**: записи с одним IP склеиваются в одну карточку
   «N. ИМЯ — устройств: K, это один пользователь» с чипом `IP x.x.x.x`,
   суммами (баланс, паки, джекпоты, в банк), лучшей прогрессией альбомов и
   кнопками уровня группы («Обнулить все», «Блок. все», «Удалить все» —
   `statsZeroGroup/statsBlockGroup/statsDeleteGroup` применяют действие ко всем
   `cid` группы). Внутри — раскрывающийся список устройств: у каждого своя
   строка с иконкой форм-фактора, своим балансом, своим ID и своими кнопками.
   Записи без IP (старые клиенты) группируются по `did`, а совсем старые — как
   раньше, по одной; им показываются чипы «IP не сообщил» / «устройство
   неизвестно».
3. **Тумблер** в шапке панели: «Один IP = 1 пользователь: вкл/выкл»
   (`nx_stats_group_ip`), выключенный возвращает прежний вид «строка на
   устройство». Сводка теперь показывает «Пользователей · устройств».

Проверка (`tools/test-b363.js`, скриншот `tools/shots/b363-users-panel.png`):
две записи с IP 95.214.22.7 (Android-телефон + iPadOS-планшет) стали одной
карточкой с суммой 44.3k и списком из двух устройств; «Обнулить все» пометил
оба `cid` в `siteStats.z`; своя запись опубликовала `ip/dev/did`; 40 циклов
heartbeat-рендера без ошибок; дымовой тест сайта — 0 ошибок.

Приватность: реестр textdb читается без авторизации, поэтому IP и портрет
устройства видны любому, кто знает адрес документа. Это осознанный компромисс
админ-инструмента: поле `ip` хранится как есть (без маскировки), чтобы
группировка работала; при желании маскируется заменой последнего октета в
`siteStatsDoc`.

## 8. b364: общий баланс и прогресс между устройствами одного пользователя

Панель (b363) показала устройства одного человека отдельными строками, но игра
хранила прогресс **в каждом браузере отдельно**: телефон, планшет и ПК одного
владельца жили разными балансами и коллекциями.

### 8.1. Как связываются устройства

* **Код профиля** — главная привязка: на основном устройстве «Создать код»
  (6 знаков), на остальных «Ввести код» или открыть ссылку `…?prof=КОД`
  (подхватывается из URL само). Профиль = документ
  `textdb.dev/api/data/nexus-tcg-prof-c-<код>`.
* **Авто по IP** — если кода нет, устройства с одним IP попадают в общий
  документ `nexus-tcg-prof-i-<hash(ip)>` (hash, сам IP в имя не пишется).
  Отключается тумблером «Авто по IP». Код всегда важнее IP.
* Синхронизация: при загрузке, каждые 45 с, при скрытии вкладки (keepalive-пуш,
  чтобы дельта не потерялась с закрытой вкладкой) и кнопкой «Синхронизировать
  сейчас» в Студии → «Синхронизация между устройствами».

### 8.2. Правило слияния (выбрано владельцем)

* **Баланс — «последнее состояние + дельта»**: устройство пушит не свой баланс,
  а ИЗМЕНЕНИЕ с момента своей прошлой синхронизации (`nx_prof_lastbal`), которое
  прибавляется к общему значению. Заработанное офлайн на втором устройстве
  прибавляется, потраченное — вычитается, двойного счёта нет.
  Критично: после подтягивания общего значения база «моих изменений»
  обновляется даже без пуша — иначе подтянутый прирост уезжал в облако вторично
  (тест это поймал: +50 дублировались, трата откатывалась).
* **Прогресс — объединение**: паки и карты union по id, коллекция/альбомы/
  достижения/статистика — максимум по ключам, колода — объединение с фильтром
  по имеющимся картам, ежедневка/задания — более свежие по дате, уровень кирки
  шахты — максимум.
* Защита от перезаписи: после пуша документ перечитывается, если между пушем и
  чтением вписалось другое устройство — ещё один цикл слияния.

### 8.3. Панель

У синхронизированных устройств в карточке пользователя появляется бейдж
«синхронизированы: код …», и агрегаты считаются **максимумом**, а не суммой
(баланс у таких устройств общий, сумма задвоила бы его); в реестр публикуется
поле `prof` (код или «IP-авто»).

### 8.4. Проверено (`tools/test-b364.js`, мок textdb, два независимых контекста)

```
A 1000 + B 50 по коду TEST01      -> у обоих 1050, карты union c1+c2
A заработал +200 офлайн           -> у обоих 1250 (дельта, без двойного счёта)
B потратил 250                    -> у обоих 1000
C и D без кода, один IP           -> общий IP-документ, 10+5 = 15 у обоих

ошибок страниц: 0
```

## 9. b365: привязка устройств через QR-код

Ручной ввод кода (b364) остался, но основной сценарий теперь — QR:

* **«QR-код»** в блоке синхронизации показывает QR ссылки
  `<адрес сайта>/?prof=КОД` (кода ещё нет — создаётся автоматически).
  Сканировать можно **обычной камерой телефона**: откроется сайт и сам
  привяжет устройство по параметру URL (`profInit` это умеет с b364);
* **«Сканировать QR»** открывает существующий камера-сканер переноса
  прогресса (`qrGoScan` + jsQR). В `qrxHandleCode` добавлена ветка: если в
  отсканированном тексте есть `?prof=КОД` или он имеет вид `NXPROF:КОД` —
  устройство привязывается к профилю (вместо переноса прогресса), сканер
  закрывается, запускается синхронизация. `qrxLooksLikeCode` такие коды
  теперь пропускает (важно для системного сканера Telegram, который чужие
  форматы игнорирует);
* свой QR рисуется тем же генератором и тем же уровнем коррекции L, что и коды
  переноса (`qrcode(0,'L')`, крупный модуль 8px — читается камерой с экрана).

Проверено `tools/test-b365.js` (полный цикл в headless): модалка открылась,
код создан, canvas нарисован (26560 тёмных пикселей), **нарисованный QR
декодирован собственным jsQR сайта** обратно в ссылку `?prof=M6CQVP`,
«скан» чужой ссылки применил код `QR77XK` и создал документ профиля
`nexus-tcg-prof-c-qr77xk`; ошибок страниц 0. Скриншот:
`tools/shots/b365-profile-qr.png`. Дымовой тест сайта после правки: 0 ошибок.

Версия сборки nxmob9 → nxmob10 (сброс cache-first кэша service worker).

## 10. b366: один QR = прогресс + профиль; самопроверка читаемости QR

Кнопка QR в навбаре («Перенос прогресса») раньше несла только снимок прогресса.
Теперь в тот же QR зашит **код профиля синхронизации** (b364): отсканировавшее
устройство и прогресс получает (экран подтверждения), и к профилю привязывается
сразу — баланс и прогресс становятся общими без ручного ввода кода.

* `qrxBuild()` добавляет в снимок `prof` (код создаётся, если его не было);
  статус модалки пишет «в QR также код профиля …»;
* `qrxHandleCode()` в ветках relay/direct/JSON зовёт `qrxApplyProf()`: код
  профиля применяется до экрана подтверждения переноса;
* после «Принять» база дельт профиля ставится в **привезённый** баланс
  (`p.c`), а на 2.5 с включается `profHold()` — фоновая синхронизация не
  перетирает привезённый сейв и не двойнит перенос (гонка найдена тестом:
  фоновый синк, стартовавший до accept, досчитывал привезённый баланс как
  «свою дельту» — 8842 вместо 4321);
* локальные бонусы после accept (достижения и т.п.) уходят в общий профиль
  обычной дельтой — устройства сходятся в одном числе.

### 10.1. Самопроверка QR (попутная находка)

Замер показал: jsQR читает с канваса НЕ любой нарисованный QR — у плотных
версий бывают неудачные сочетания маски/версии:

| длина кода | модулей | jsQR с чистого канваса |
|---|---|---|
| 60–800 | 33–97 | читает |
| **1040** | **109** | **НЕ читает** |
| 1400 | 125 | читает |

Поэтому `qrxBuild()` после отрисовки прямого кода прогоняет
`qrxSelfCheck()`: рисованный QR декодируется собственным jsQR сайта, и если

## 11. b367: СРОЧНОЕ лечение «у пользователей обнуляется заработанный баланс»

Жалоба появилась после b364. Найдены две причины, обе в синхронизации профиля:

### 11.1. Авто-связка по IP была включена ПО УМОЛЧАНИЮ у всех

За одним публичным IP мобильного провайдера (CGNAT) сидят сотни посторонних
людей. Их устройства молча попадали в один профиль-документ и «сливали»
балансы: чужой смартфон мог обнулить/перемешать чужие же накопления.
Теперь `profIpAuto()` по умолчанию **ВЫКЛ**; связка по IP работает только
если владелец сам включил тумблер «Авто по IP». Группировка в панели
«Пользователи» (b363) по-прежнему показывает устройства с одним IP как
одного пользователя — это витрина, она балансы не трогает.

### 11.2. Правило «doc + моя дельта» теряло дельты при параллельных пушах

Два устройства профиля читают документ одновременно: A пушит `doc+dA`,
B пушит `doc+dB` поверх (не увидев dA) — взнос dA исчезал из дока; на
следующем круге A пересчитывался от урезанного дока и **заработанное
испарялось**. Тот же эффект при сбросе/пересоздании дока (textdb) и при
аварийном keepalive-пуше.

Лечение — **леджер накопительных взносов** (`mov`):

* баланс профиля = `base + Σ mov[did]`, где `mov[did]` — накопительный взнос
  устройства (сколько оно принесло в профиль за всё время);
* устройство перезаписывает **только свою** строку `mov`, беря её из своего
  LS (`nx_prof_movc`) плюс дельта с последней синхронизации;
* если своей строки в доке нет или она не совпадает с расчётом (`movLost`) —
  пуш происходит принудительно: потерянный взнос **самовосстанавливается**
  следующей синхронизацией автора, чужие устройства на ноль не садятся;
* база `lastBal` двигается на применённый баланс только когда своей дельты
  в круге не было (иначе подтянутое чужое поехало бы в облако как «своё»);
  при неудачном пуше база не трогается — дельта повторится;
* аварийный пуш при скрытии вкладки считает по тому же леджеру и не трогает
  LS (не дошёл — дельту подберёт следующий круг);
* доки v1 без леджера мигрируют: `base = coins − Σ mov` (т.е. старое значение),
  ничего не теряется.

## 14. b370: «лишние повторки» и «продал — а количество не уменьшилось»

Жалоба: в альбомах растёт число повторок, которых игрок не зарабатывал, а
после «Продать все повторки» количество не уменьшается.

### 14.1. Причина (обе — в правиле слияния профиля b364)

* Коллекция сливалась **максимумом** по ключам: устройство A продало копию
  (3→2), устройство B при синхронизации приносило своё 3 — максимум снова
  давал 3. Продажа «откатывалась» на всех устройствах.
* Паки сливались **объединением**: пак, вскрытый на A, возвращался с B как
  «невскрытый» — его можно было вскрыть второй раз → оттуда и «лишние
  повторки», которые игрок не зарабатывал.
* Карты-экземпляры тоже объединялись, поэтому проданная/исчезнувшая карта
  воскресала из копии второго устройства.

### 14.2. Лечение: леджер взносов коллекции + tombstone паков

* `collection` больше не max и не union: баланс копий = `base_col + Σ colmov[did]`,
  где `colmov[did]` — накопительный взнос устройства (его собственные открытия
  и продажи с момента привязки, дельтами от снимка `nx_prof_colsnap`).
  Продажа на любом устройстве — отрицательная дельта — вычитается у всех.
* Паки: union минус **tombstone** (`ptomb`) — id вскрытых/проданных/удалённых
  паков. Вскрыл на одном устройстве — исчез везде, повторно не всплывает.
* Карты-экземпляры выводятся из слитой коллекции: `cards = union(объекты) ∩
  {collection[id] > 0}`, поэтому «повторки» в альбомах всегда согласованы с
  продажами; колода фильтруется так же.
* Счётчики, которые в игре только растут (stats, достижения, packStats,
  albumBonus, pity), остались максимумом — для них это безопасно.
* Миграция: доки v2 без `colmov` получают `base_col = collection` из дока,
  взносы стартуют с нуля — ничего не теряется и не двоится.
* Попутно (b370): отпечаток `profSig()` для b368 сделал детерминированным
  (сортировка ключей JSON и id) — иначе перерисовка вспыхивала от порядка
  ключей после union.

## 18. b374: «куда пропали карточки» — первый синк устройства стирал его коллекцию

Жалоба владельца после b370–b373: у устройства пропали карты.

### 18.1. Причина (регрессия леджера коллекции b370)

`profMergeState` считает вклад устройства в коллекцию как дельту от снимка
`nx_prof_colsnap`. На ПЕРВОМ синке устройства снимка ещё нет — дельта
считалась пустой, вклад `{}`, а слитая коллекция = `base_col + Σ colmov`
(чисто облачный леджер). `profApply` перезаписывала этим локальное
состояние — и все карты устройства, которых не было в леджере профиля,
**стирались навсегда** (в леджер они тоже не попадали).

Три проявления:

1. Второе устройство привязывается кодом/QR к существующему профилю —
   его собственная коллекция заменяется облачной (вплоть до полной потери).
2. Любое устройство после выкладки b370: снимков `nx_prof_colsnap` до b370
   не существовало, поэтому первый же синк откатывал коллекцию к состоянию
   документа — карты, открытые с момента последнего пуша, пропадали.
3. Смена кода профиля не очищала ключи леджера (`nx_prof_colmov/colsnap/
   ptomb/packsnap`): снимок чужого профиля давал огромные отрицательные
   дельты и мог стереть карты уже нового профиля.

Тест b370 этого не поймал: сценарий «B привязался и сохранил свою карту c2»
в `test-b364.js` только ПЕЧАТАЛСЯ («ожидаем c1,c2»), но в итоговые
assertions не входил — при прогоне перед правкой печаталось `карты: c1`.

Попутно найдено: в анти-клоббер ветке (перепроверка после гонки пушей)
`profMergeState(profSnap(), r2)` вызывалась БЕЗ документа и id устройства —
`base_col` строился от локальной коллекции, а сверху плюсовался собственный
взнос (двойной счёт), чужие взносы терялись, снимки после ветки не
продвигались.

### 18.2. Лечение

* **Миграция первого подключения**: если снимка нет, а документ есть —
  вклад устройства = `profMapExcess(локальная коллекция, база+чужие взносы)`
  (только положительный излишек). Свои/лишние карты выживают и попадают в
  леджер; общие карты НЕ двоятся (в отличие от наивного «вся коллекция =
  вклад»). Устройство, которое уже всё получило из профиля (например,
  переносом QR), даёт нулевой вклад — ничего не дублируется.
* **Цепочка снимков привязана к коду профиля** (`nx_prof_colcode`): снимки,
  взносы и tombstone читаются, только если код совпадает; при смене кода
  устройство входит в новый профиль чистой миграцией (п. 1). Записывается
  после успешного пуша и при продвижении снимков без пуша.
* **Нет документа — нет старых взносов**: `colmov = {}`, вся локальная
  коллекция уходит в `base_col` (раньше залежалый `nx_prof_colmov`
  плюсавался к базе → удвоение копий после потери/пересоздания дока).
* **Анти-клоббер ветка**: `profMergeState(profSnap(), r2, chk, did)`,
  в док публикуется свежий `f2.__pub`, снимки/взносы продвигаются и после
  второго пуша.
* Тест: проверки b374 доведены до assertions (карты c1,c2 у B теперь
  обязательны), добавлены сценарии «первое подключение», «смена профиля»,
  «потеря документа»; устройства E и C объединены в одно (браузер песочницы
  не вывозил 4-й контекст — тест зависал).

## 19. b375: «я загружал по-своему, а ты их перемешал» — порядок карт закреплён нумерацией

### 19.1. Жалоба и диагноз

Владелец: «Что случилось с порядком карт? Я их загружал по-своему, а ты их
перемешал. Я решаю, в каком порядке загружать карты. И в создание карт добавь
нумерацию, чтобы не было больше такого».

Виновник — слияние синхронизации профиля (b370/b374). Порядок массива карт
собирался из объединения ключей словаря определений:

```js
const cm = {};
(R.cards || []).forEach(c => cm[c.id] = c);   // облако первым
(L.cards || []).forEach(c => cm[c.id] = c);
out.cards = Object.keys(cm).filter(...)...    // порядок = порядок вставки ключей
```

`Object.keys` даёт «облачный документ first, локальные довеском», поэтому после
каждой синхронизации `state.cards` перестраивался в порядок документа, а карты,
долитые локально, уезжали в хвост. То же происходило с паками (`Object.keys(pm)`)
и колодой (`Object.keys(dk)`). Порядок загрузки владельца не хранился нигде.

### 19.2. Лечение: явная нумерация `ord` + детерминированная сортировка

* **Ключ сортировки** `cardSortKey(c)`: явный `c.ord`, а пока его нет — время
  создания из id (`card-<время>[-<индекс в партии загрузки>]`, у массовых
  загрузок индекс = позиция строки в списке владельца). Непарсящиеся id — в
  конец, сортировка устойчивая. Тай-брейк по id детерминированный: на всех
  устройствах порядок одинаков.
* **`cardsSortNorm()`**: сортирует `state.cards` и проставляет явный `ord`
  каждой карте (порядок больше не зависит от парсинга id). Вызывается после
  каждого входа состояния в игру: слияние профиля (`profApply`), импорт сейва,
  полный сброс, комнатная синхронизация (`cloudMerge`), досев стандарта
  (`reseedStandard`), покупка на бирже.
* **Разовая миграция при загрузке** (`migrateCardOrderB375`): восстанавливает
  порядок создания/загрузки из id и проставляет номера — уже перемешанные
  сохранения возвращаются в исходный порядок владельца.
* **Создание карт получает номер сразу**: одиночное — `ord: nextCardOrd()`
  (следующий за максимумом), массовое — `ordBase + i*10` по строкам списка:
  порядок загрузки закреплён в момент загрузки.
* **Слияние (`profMergeState`)**: `out.cards` сортируется `cardSortCmp`,
  `out.packs` — `packSortCmp` (время создания пака), `out.deck` — по номерам
  карт. Номер при конфликте берётся у стороны, которая **последней меняла
  порядок**: метка `ordAt` (LWW) ставится в `moveCardInPack`, поэтому ручная
  перестановка с одного устройства доезжает до остальных и не откатывается
  чужим пушем.
* **Нумерация в Студии**: у каждой карточки бейдж `№N` (позиция в паке =
  порядок владельца) и кнопки ↑/↓ (`moveCardInPack`) — владелец переставляет
  карты вручную, обмен номерами с соседом + `ordAt` + `profSyncSoon()`.
  `ord`/`ordAt` добавлены в `STD_CARD_FIELDS` — перестановка стандартных карт
  доезжает до комнаты патчами.
* **Перестановка обязана уехать в облако**: отпечаток `profSig()` теперь
  содержит порядок карт (несортированный список id), а `profSyncOnce` пушит,
  если `sigMine !== LS['nx_prof_pushsig']` (отпечаток запоминается после
  успешного пуша, включая анти-клоббер `doc2`). Раньше перестановка не меняла
  ни один критерий `needPush` и молча оставалась локальной.

### 19.3. Проверено (`tools/test-b375.js`, 13 проверок, nxmob20)

## 21. b377 — «у пользователей не загружаются картинки карт, особенно на мобильных»

Жалоба: главная функция игры — загрузка карточек, а картинки карт у игроков не
грузятся; на телефонах особенно. Замер в эмуляции iPhone 12 (DPR 3, как в
Telegram Mini App) на 36 РЕАЛЬНЫХ артах облачного каталога «Доктор Кто»
(`media/card_mv03*_doktor.png`, 1080×1920 по 1.6-4.3 МБ): альбом тянул
**172 МБ артов и 248 МБ распакованных битмапов**. На телефоне это и есть
«картинки не приехали» / «браузер закрылся».

### 21.1. Причина №1: патч сборщика заменял только ПЕРВОЕ вхождение

`tools/build.py: patch_once()` делал `text.replace(old, new, 1)`, а в лог
печатал ПОЛНОЕ число найденных вхождений. Сборка рапортовала
«albumCardHTML: <img> обеих веток (компакт + обычная) **(2 вхожд.)**» — и молча
заменяла только первую. Обычная ветка `albumCardHTML` осталась на
`src="${mediaUrl(card.image)}"`, то есть на МАСТЕРЕ.

Вид «Сетка» — вид альбома по умолчанию. Значит, каждый игрок, открывая альбом,
получал 50 мастеров по 2-4 МБ вместо миниатюр `media/t2/` по 62 КБ. Ровно та же
ошибка оставила мастер в плитке лота биржи (вид «Сетка»).

**Лечение:** `patch_once()` теперь заменяет ВСЕ вхождения и принимает `want` —
ожидаемое число вхождений; при расхождении сборка падает громко
(`AssertionError`), а не собирает половину патчей. Все списки мест
(ALBUM_SITES / THUMB_SITES / CV_SITES) получили явные `want`.

### 21.2. Причина №2: фоновый автокэш качал мастера у каждого игрока

`nxAutoCacheOnce()` (qr-transfer.js) каждые 60 секунд ставила в очередь по 10
МАСТЕРОВ из каталога — ~30 МБ фонового трафика в минуту на каждом устройстве,
без участия игрока. Поток забивал мобильный канал (видимые карточки не успевали
прогрузиться) и наполнял IndexedDB файлами, которые на экране не рисуются.

`nxCheckArts(true)` через 9 секунд после старта открывала 73 мастера
**одновременно** (`keys.forEach` без очереди) — на мобильной сети канал вставал.

**Лечение:** автокэш кэширует то, что реально показывается, — миниатюры
`media/t/` + `media/t2/` (в 21 раз меньше трафика, офлайн-готовность интерфейса
сохраняется). Мастера остаются только владельцу (`nxGhToken()` + авто-вшивание
или автоотправка) — они нужны автоотправке b343 в GitHub. Очередь автокэша
поднята 10 → 40 (миниатюры в 50 раз легче). `nxCheckArts` получила очередь из
3 потоков и автозапуск только при разблокированной «Студии» или токене; кнопка
«Проверить картинки» в Студии не тронута.

### 21.3. Причина №3: отозванный blob:URL ронял карту в заглушку навсегда

`IMG_OBJ` держит ≤18 blob:URL и при вытеснении вызывает
`URL.revokeObjectURL()`. Если URL ещё висел на живой `<img>`, картинка
мгновенно становилась битой, а `imgErrorChain()` по `blob:` не делала НИЧЕГО:
`raw.indexOf('http') !== 0` → ни ретраев, ни зеркала, ни кэша → сразу заглушка.
На стенде: 3 случая ДО и 11 после перевода на миниатюры (разных URL стало
больше).

**Лечение:** занятое не отзывается — уходит в `IMG_OBJ_ORPHANS` и дожигается
свопом раз в минуту, когда элемент уже вне DOM. Плюс страховка в
`imgErrorChain`: мёртвый `blob:` возвращает элемент на реальный URL арта
(`__nxHttpUrl` → `data-nx-full` → `__nxOrig`), до 3 попыток.

### 21.4. Причина №4: новые арты приезжали без миниатюр

Автоотправка b343 коммитит в `media/` только мастер. У двух последних карт
(`card_mv1t7bpz_0000_eurovision.png`, `card_mv2f8xhj_0001_755219290809350.png`)
миниатюр не было вовсе, и в `NX_EMBED_THUMB` они не значились — `nxThumbFor()`
возвращал пусто, карта грузилась мастером всегда.

**Лечение:** миниатюры для них сгенерированы (158 мелких + 84 средних).
`nxThumbFor()` при отсутствии файла в картах сборки достраивает путь по
соглашению `media/t(2)/<имя>.webp`; если файла нет на сервере, сработает
прежняя страховка `data-nx-full`. Чтобы рецидив не вернулся, добавлен `tools/thumbs_for_media.py` — догоняет
миниатюры для новых артов (те же параметры, что у build.py). Готовый workflow
для автозапуска лежит рядом с репозиторием: `deploy/media-thumbs.yml` — в коммит
он не попал, потому что токен сборки без scope `workflow` не даёт пушить
`.github/`. Добавить вручную: создать `.github/workflows/media-thumbs.yml`
с этим содержимым (Settings → Actions → permissions: contents: write).

### 21.5. Попутно

* `preloadImages()` отсекала ВСЕ встроенные арты условием
  `u.indexOf('http') === 0` (NX_EMBED_MEDIA даёт относительные `media/...`):

## 25. b381 — «картинки не загружаются» вернулись: 58 карт «Евровидения» без миниатюр + imgguard гасил карты навсегда (nxmob25)

### 25.1. Жалоба и диагноз

Жалоба та же, что в разделе 21 (b377): «у пользователей не загружаются
карточки-картинки, особенно на мобильных устройствах». Скриншот: карты #057 и
#058 пакета «Евровидение» — пустые рамки с именами, арта нет.

Найдены две независимые причины.

**Причина №1: у 58 карт «Евровидения» не было миниатюр.**
`nxThumbFor()` ищет имя файла в `NX_EMBED_THUMB` / `NX_EMBED_THUMB_MID`. Если
имени там нет, путь достраивается «по соглашению»: `media/t2/<имя>.webp`. Для
всех 58 мастеров `card_mv3*…` файла не было ни в `media/t/`, ни в `media/t2/`:

| запрос | ответ сервера |
|---|---|
| `media/t2/card_mv3xmp0a_0051_….webp` | **404** |
| `media/t/card_mv3xmp0a_0051_….webp` | **404** |
| `media/card_mv3xmp0a_0051_….png` (мастер) | 200, **4.0 МБ** |

Дальше `imgErrorChain()` честно откатывается на `data-nx-full`, то есть на
мастер. Открытый альбом «Евровидения» — это 59 запросов, из них 59×404, а затем
~125 МБ мастеров; распакованные битмапы этих 58 мастеров — **459 МБ**. Телефон
не успевает докачать: картинки «не загружаются», WebView умирает по памяти.

Почему миниатюр не было: `tools/thumbs_for_media.py` в шапке описывает GitHub
Action, который догоняет миниатюры на каждый пуш в `media/**`. **Самого файла
в `.github/workflows/` в репозитории не было** — арты, авто-отправленные b343,
оставались без миниатюр навсегда.

**Причина №2: imgguard снимал `src` и не возвращал его.**
Сторож памяти в `index.html` при >160 МБ битмапов на экране делал
`im.removeAttribute('src')` у крупных картинок за экраном, запоминая URL в
`__nxUnloaded`. Места, где `__nxUnloaded` читался бы обратно, в проекте не было
вообще: ни восстановления, ни заглушки. Сторож b252 («битые картинки») такой
элемент пропускает (`src` пуст → не http), поэтому карта оставалась пустой
**навсегда** — стоило прокрутить альбом назад. На десктопе порог почти не
достигался, на телефоне с мастерами по 2–4 МБ — постоянно; отсюда «особенно на
мобильных».

### 25.2. Лечение

1. **Миниатюры для всех 58 мастеров**: `media/t/` (256px, q72) и `media/t2/`
   (512px, q78) — параметры один в один с `tools/build.py` (`THUMB_W/THUMB_Q`,
   `MID_W/MID_Q`, `MID_MIN_SRC=640`, LANCZOS, `method=6`). 125.0 МБ мастеров →
   0.6 МБ мелких + 1.8 МБ средних; распакованные битмапы 459 МБ → 26 МБ на
   мелком уровне, то есть **−94 %**.
2. **Карты в `assets/app.js` пополнены**: `NX_EMBED_THUMB` 158→216,
   `NX_EMBED_THUMB_MID` 84→142. `nxThumbFor()` больше не ходит в
   несуществующие пути.
3. **imgguard восстанавливает картинки**: вместо `removeAttribute('src')`
   ставится прозрачная заглушка 1×1 (`NX_BLANK_GIF`; на пустом `src` WebKit
   может пойти за самим документом), а всё выгруженное возвращает
   `nxImgRestoreVisible()` — по таймеру сторожа и мгновенно на
   `scroll`/`resize`/`orientationchange` (троттлинг 120 мс), с запасом в экран
   сверху и снизу и со сбросом флагов цепочки ошибок.
4. **Кэш-тег `?v=nxmob24 → nxmob25`** (index.html, `VERSION` в sw.js,
   `BUILD_TAG` в tools/build.py) — клиенты перечитывают app.js.
5. **`tools/sync_thumb_maps.py`** — приводит `NX_EMBED_THUMB` /
   `NX_EMBED_THUMB_MID` в `assets/app.js` в соответствие с фактом на диске:
   карта строится только по существующим файлам, поэтому не может указать в
   404. Флаги: `--check` (код 1 при расхождении, для CI) и `--bump-version`
   (поднимает `?v=`/`VERSION`/`BUILD_TAG`, и только когда app.js изменился).
6. **`tools/media-thumbs.yml`** — тот самый экшен из шапки
   `thumbs_for_media.py`: на пуш в `media/**` догоняет миниатюры,
   синхронизирует карты и коммитит обратно через `GITHUB_TOKEN` (сам себя не
   перезапускает). В `.github/workflows/` не положен: у токена коммита не было
   scope `workflow`, GitHub отклоняет такие tree-entry. См. 25.4.
